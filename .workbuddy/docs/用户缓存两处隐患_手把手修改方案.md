# 用户缓存两处隐患 —— 手把手修改方案

> 本文档只做「讲解 + 建议 diff」。**没有修改任何源码**。
> 相关源码位置：`shiguang-user/shiguang-user-biz/src/main/java/com/quanshiguang/shiguang/user/biz/`

---

## 阅读前的三个已核实事实

这三个事实决定了「怎么改才是对的」，先把它们钉住：

1. **Redis value 用 `Jackson2JsonRedisSerializer(Object.class)` 序列化**（`config/RedisTemplateConfig.java` 第 30 行）。
   → `set(key, "null")` 存进去的字节是 JSON 字符串字面量 `"null"`（带引号，6 字节）；读出来是 Java 的 `String "null"`（4 字符）。

2. **`JsonUtils.parseObject("null", XxxClass.class)` 返回 `null`**（`JsonUtils.java` 第 60-66 行）。
   → `"null"` 不是空白串，会走到 `OBJECT_MAPPER.readValue("null", clazz)`，Jackson 读到 JSON 的 null 值，返回 Java null。

3. **`LOCAL_CACHE` 是 `Cache<Long, FindUserByIdRspDTO>`，Caffeine 不允许 value 为 null**。
   → `LOCAL_CACHE.put(userId, null)` 会抛 NPE。

---

# 隐患一：本地缓存只写不删（多实例脏数据）

## 现状

`findById` 会往本地缓存写（第 400 行），`updateUserInfo` 只删 Redis（第 205 行 `deleteUserRedisCache`）。
全模块搜索确认：`LOCAL_CACHE` **只有 `put`，没有任何一处失效删除**。

结果：用户服务部署 N 个实例时，改完昵称 → 只有**处理这次请求的那个实例**的 Redis 被删；
另外 N-1 个实例的本地缓存里仍是旧昵称，最长脏 **1 小时**（`expireAfterWrite(1, TimeUnit.HOURS)`）。

对照组：note / comment 模块都有**广播模式**的本地缓存失效 Topic，user 没有。

## 三档方案

### 方案 A —— 当前实例删除（1 行，推荐先做）

**位置**：`UserServiceImpl.updateUserInfo` 第 203-213 行

```java
        if (needUpdate) {
            // 删除用户缓存
            deleteUserRedisCache(userId);
            LOCAL_CACHE.invalidate(userId);   // ← 新增：清掉当前实例的本地缓存

            // 更新用户信息
            userDO.setUpdateTime(LocalDateTime.now());
            userDOMapper.updateByPrimaryKeySelective(userDO);

            // 延时双删
            sendDelayDeleteUserRedisCacheMQ(userId);
        }
```

**或者**（更规范，但需要重命名方法）并进 `deleteUserRedisCache`：

```java
    private void deleteUserRedisCache(Long userId) {
        // 构建 Redis Key
        String userInfoRedisKey = RedisKeyConstants.buildUserInfoKey(userId);
        String userProfileRedisKey = RedisKeyConstants.buildUserProfileKey(userId);

        // 删除当前实例的本地缓存（Caffeine，进程私有）
        LOCAL_CACHE.invalidate(userId);
        PROFILE_LOCAL_CACHE.invalidate(userId);   // 注意：该缓存目前是死代码，可按需保留

        // 批量删除 Redis
        redisTemplate.delete(Arrays.asList(userInfoRedisKey, userProfileRedisKey));
    }
```

⚠️ 若采纳后一种写法，方法名 `deleteUserRedisCache` 就不准了，建议同步改名为 `deleteUserCache`
（IDEA 里选中方法名按 `Shift + F6`，调用点会自动跟着改）。

**效果**：把「1 小时脏数据」压缩到「极小概率的竞态窗口」。
**代价**：1 行代码 + 一次同步内存操作（微秒级）。

### 方案 B —— 广播失效（彻底，照抄 note 的写法，5 步）

参照物：`shiguang-note` 的 `TOPIC_DELETE_NOTE_LOCAL_CACHE` + `DeleteNoteLocalCacheConsumer`。

**第 1 步**：`constant/MQConstants.java` 加常量

```java
    /**
     * Topic 主题：删除用户本地缓存
     */
    String TOPIC_DELETE_USER_LOCAL_CACHE = "DeleteUserLocalCacheTopic";
```

**第 2 步**：`service/UserService.java` 接口加方法

```java
    /**
     * 删除用户本地缓存
     *
     * @param userId
     */
    void deleteUserLocalCache(Long userId);
```

**第 3 步**：`service/impl/UserServiceImpl.java` 实现

```java
    @Override
    public void deleteUserLocalCache(Long userId) {
        LOCAL_CACHE.invalidate(userId);
    }
```

**第 4 步**：新建 `consumer/DeleteUserLocalCacheConsumer.java`（新文件）

```java
package com.quanshiguang.shiguang.user.biz.consumer;

import com.quanshiguang.shiguang.user.biz.constant.MQConstants;
import com.quanshiguang.shiguang.user.biz.service.UserService;
import jakarta.annotation.Resource;
import lombok.extern.slf4j.Slf4j;
import org.apache.rocketmq.spring.annotation.MessageModel;
import org.apache.rocketmq.spring.annotation.RocketMQMessageListener;
import org.apache.rocketmq.spring.core.RocketMQListener;
import org.springframework.stereotype.Component;

@Component
@Slf4j
@RocketMQMessageListener(consumerGroup = "shiguang_group_" + MQConstants.TOPIC_DELETE_USER_LOCAL_CACHE, // Group
        topic = MQConstants.TOPIC_DELETE_USER_LOCAL_CACHE, // 消费的主题 Topic
        messageModel = MessageModel.BROADCASTING) // 广播模式：每个实例都要收到
public class DeleteUserLocalCacheConsumer implements RocketMQListener<String> {

    @Resource
    private UserService userService;

    @Override
    public void onMessage(String body) {
        Long userId = Long.valueOf(body);
        log.info("## 消费者消费成功, userId: {}", userId);

        userService.deleteUserLocalCache(userId);
    }
}
```

**第 5 步**：`updateUserInfo` 里发送

```java
        if (needUpdate) {
            // 删除用户缓存
            deleteUserRedisCache(userId);

            // 同步发送广播模式 MQ，将所有实例中的本地缓存都删除掉
            rocketMQTemplate.syncSend(MQConstants.TOPIC_DELETE_USER_LOCAL_CACHE, userId);

            // 更新用户信息
            userDO.setUpdateTime(LocalDateTime.now());
            userDOMapper.updateByPrimaryKeySelective(userDO);

            // 延时双删
            sendDelayDeleteUserRedisCacheMQ(userId);
        }
```

**广播模式的三个坑（务必知道）**：

1. **不保证不丢**。广播模式的消费位点存在**本地文件**（默认 `~/rocketmq_offsets`），
   实例重启或下线期间的消息**不会补投**。所以广播只适合「缓存失效」这类可容忍丢失的场景——
   这正是它在 note / comment 里的用法。
2. **`syncSend` 会增加接口耗时**，等于在改资料这条路上多一次同步网络往返。
   note 也是这么写的，可以接受；若在意，改成 `asyncSend` + 回调。
3. **group 名要固定，不要加实例标识**。广播模式下同一个 group 的**每个实例都会收到全量消息**，
   这本身就是广播的定义。写成 `"shiguang_group_" + TOPIC` 是正确做法。

### 方案 C —— 缩短 TTL / 干脆不要本地缓存（不推荐）

把 `LOCAL_CACHE` 的 `expireAfterWrite` 从 1 小时改成 1~5 分钟，或直接删掉本地缓存只留 Redis。

- 优点：零新增代码，改一行常量。
- 缺点：Caffeine 的存在意义就是挡住 Redis 的网络 IO；降 TTL 会显著抬高 Redis QPS。
- 结论：**不建议**，除非只是想临时止血。

### 推荐路径

**方案 A 先上（1 行）→ 有余力再补方案 B（5 个文件）。**

## ⚠️ 方案 A / B 都挡不住的一个竞态（进阶）

本地缓存的**写入是异步的**（第 400 行 `threadPoolTaskExecutor.submit`），但**删除是同步的**。
两者之间有一个窗口：

| 时刻 | 请求 A（查） | 请求 B（改） | 结果 |
|---|---|---|---|
| t1 | 查 DB，拿到**旧值** | | |
| t2 | 提交异步任务 T1 写本地缓存 | | |
| t3 | | 删 Redis + 删本地缓存 + 广播 | |
| t4 | | 写 DB（新值） | |
| t5 | **T1 才执行，把旧值写回本地缓存** | | 👈 脏 |

也就是说：**「异步回填 + 失效」天生存在覆盖竞态**。
- 方案 A/B 能把它压到「极小概率」，但压不到零。
- 彻底的解法是把回填改成**同步**，或改用 Caffeine 的原子加载 `LOCAL_CACHE.get(key, mappingFunction)`。
  但后者会把 Redis / DB 查询塞进 loading function，还会因为 Caffeine 对同 key 加锁而放大延迟，
  且这里的查询路径带 `BizException` 语义，改造起来不轻松。**建议先不做。**
- 兜底：TTL 1 小时保证了脏数据最多活 1 小时，不会永久错。

# 隐患二：空值缓存导致「第一次报错、第二次返回成功但数据为空」

## 精确诊断（四步）

复现路径：查一个**不存在的 userId**，连查两次。

**第一次请求**（Redis 里没有该 key）

1. 本地缓存 miss → Redis miss → 查 DB → `userDO` 为 null
2. 异步线程写空值标记：`set(userInfoRedisKey, "null", 60 + random(60), SECONDS)`
3. `throw new BizException(ResponseCodeEnum.USER_NOT_FOUND)` ✅ 正确

**第二次请求**（同一个 ID，空值标记还在）

4. 本地缓存 miss → Redis **命中**
5. `StringUtils.isNotBlank("null")` → **true**（它是 4 个字符，不是空白串）
6. `JsonUtils.parseObject("null", FindUserByIdRspDTO.class)` → **返回 null**
7. 异步线程里 `LOCAL_CACHE.put(userId, null)` → **Caffeine 抛 NPE**
   （注意这里用的是 `submit`，返回的 `Future` 会把异常**静默吞掉**，连日志都没有）
8. `return Response.success(null)` → **`success = true`，`data = null`** ❌

**结果**：同一个不存在的用户，第一次返回 `success:false / USER_NOT_FOUND`，
第二次返回 `success:true / data:null`。前端按 `success` 分支处理，行为前后不一致。

作者在第 414 行的注释里写了「防止缓存穿透，将空数据存入 Redis 缓存」——
**空值是写了，但读取侧从来没识别过这个标记**。这是典型的「写了一半」。

## 修改方案（最小改动，4 行）

### 改动 1：`RedisKeyConstants.java` 新增常量，消灭魔数

```java
    /**
     * 缓存空值标记：用于防止缓存穿透
     */
    public static final String NULL_CACHE_VALUE = "null";
```

### 改动 2：`UserServiceImpl.findById` 第 396-405 行

改前：

```java
        // 若 Redis 缓存中存在该用户信息
        if (StringUtils.isNotBlank(userInfoRedisValue)) {
            // 将存储的 Json 字符串转换成对象，并返回
            FindUserByIdRspDTO findUserByIdRspDTO = JsonUtils.parseObject(userInfoRedisValue, FindUserByIdRspDTO.class);
            // 异步线程中将用户信息存入本地缓存
            threadPoolTaskExecutor.submit(() -> {
                // 写入本地缓存
                LOCAL_CACHE.put(userId, findUserByIdRspDTO);
            });
            return Response.success(findUserByIdRspDTO);
        }
```

改后：

```java
        // 若 Redis 缓存中存在该用户信息
        if (StringUtils.isNotBlank(userInfoRedisValue)) {
            // 将存储的 Json 字符串转换成对象
            FindUserByIdRspDTO findUserByIdRspDTO = JsonUtils.parseObject(userInfoRedisValue, FindUserByIdRspDTO.class);

            // 命中的是「防穿透空值标记」，说明该用户不存在。
            // 必须与首次查询保持一致的语义：抛业务异常，而不是返回 success(null)
            if (Objects.isNull(findUserByIdRspDTO)) {
                throw new BizException(ResponseCodeEnum.USER_NOT_FOUND);
            }

            // 异步线程中将用户信息存入本地缓存
            // 用 execute 而非 submit：submit 会把异常吞进 Future，连日志都不打
            threadPoolTaskExecutor.execute(() -> LOCAL_CACHE.put(userId, findUserByIdRspDTO));

            return Response.success(findUserByIdRspDTO);
        }
```

### 改动 3：第 417 行写空值时改用常量

```java
                redisTemplate.opsForValue().set(userInfoRedisKey, RedisKeyConstants.NULL_CACHE_VALUE, expireSeconds, TimeUnit.SECONDS);
```

# 隐患三（顺带挖出来的）：`findByIds` 会返回 null 元素，甚至抛 NPE

小秋追隐患二时往上多看了一眼，发现同一个根因在批量接口里更严重。

**位置**：`UserServiceImpl.findByIds` 第 458-491 行

```java
        List<Object> redisValues = redisTemplate.opsForValue().multiGet(redisKeys);
        if (CollUtil.isNotEmpty(redisValues)) {
            // 过滤掉为空的数据
            redisValues = redisValues.stream().filter(Objects::nonNull).toList();
        }
        ...
            findUserByIdRspDTOS = redisValues.stream()
                    .map(value -> JsonUtils.parseObject(String.valueOf(value), FindUserByIdRspDTO.class)).toList();
```

**问题**：`filter(Objects::nonNull)` **过滤不掉字符串 `"null"`**（它是非 null 的）。
于是 `parseObject` 把它转成 `null`，`findUserByIdRspDTOS` 里就混进了一个 **null 元素**。

**后果 A —— 返回脏数据**：
入参 `[1, 2, 999]`（999 不存在但已缓存空值）→ `redisValues` 过滤后仍有 3 个 →
`findUserByIdRspDTOS` 长度也是 3 → 第 475 行 `size 相等` 成立 → 直接
`return Response.success([dto1, dto2, null])`。
**前端遍历这个数组时拿到 null，极易 NPE。**

**后果 B —— 直接抛异常**：
入参 `[1, 999, 888]`（999 有空的标记，888 完全没缓存）→
`findUserByIdRspDTOS` 长度 2，`userIds` 长度 3，不相等 → 走到第 485 行：

```java
            Map<Long, FindUserByIdRspDTO> map = findUserByIdRspDTOS.stream()
                    .collect(Collectors.toMap(FindUserByIdRspDTO::getId, p -> p));
```

`p` 是 null → `p.getId()` → **NullPointerException**，接口直接 500。

### 修改方案（2 行）

```java
        // 如果缓存中不为空
        if (CollUtil.isNotEmpty(redisValues)) {
            // 过滤掉为空的数据，以及「防穿透空值标记」
            redisValues = redisValues.stream()
                    .filter(Objects::nonNull)
                    .filter(value -> !Objects.equals(String.valueOf(value), RedisKeyConstants.NULL_CACHE_VALUE))
                    .toList();
        }
```

```java
        if (CollUtil.isNotEmpty(redisValues)) {
            findUserByIdRspDTOS = redisValues.stream()
                    .map(value -> JsonUtils.parseObject(String.valueOf(value), FindUserByIdRspDTO.class))
                    .filter(Objects::nonNull)   // 兜底：防止 null 元素进入结果集
                    .toList();
        }
```

# 怎么验证改对了

## 隐患二 / 三（只需 MySQL + Redis，不用起全套中间件）

1. 用一个不存在的 userId 调 `POST /user/user/findById`（走 Feign 或直接打 user 服务）：
   - **改前**：第一次 `success:false / USER_NOT_FOUND`；立刻再调一次 → `success:true / data:null`
   - **改后**：两次都应是 `USER_NOT_FOUND`
2. Redis 里执行 `GET user:info:<那个ID>`，确认存的就是 `"null"`（带引号是正常的，那是 Jackson 的字符串字面量），TTL 在 60~120 秒之间。
3. 批量接口打一组混合 ID：`[存在的1, 存在的2, 有空标记的999, 完全没缓存的888]`
   - **改前**：可能返回含 null 的数组，或直接 500（NPE）
   - **改后**：只返回 1 和 2，长度 2，无 null 元素

## 隐患一（需要 >= 2 个实例）

1. 实例 A、实例 B 都查一遍同一个 userId（让两边本地缓存都热起来）
2. 走 `POST /user/user/update` 改昵称
3. 立刻分别查 A、B：
   - **改前**：B 返回旧昵称，最长持续 1 小时
   - **方案 A 后**：A 立刻新昵称，B 仍可能旧（最长 1 小时）
   - **方案 B 后**：A、B 都应立刻返回新昵称

## 回归检查点

- `findUserProfile` 的两大段注释代码、`PROFILE_LOCAL_CACHE` 死代码：**本次不要动**，容易夹带风险。
- `updateUserInfo` 的调用顺序（删缓存 → 写库 → 延时双删）**不要调整**。
- `LOCAL_CACHE.invalidate` 是 Caffeine 的 API，与 `put` 同源，无额外依赖。

# 一句话总结

| 隐患 | 根因 | 最小修法 | 行数 |
|---|---|---|---|
| 本地缓存只写不删 | 缺失效入口 | `LOCAL_CACHE.invalidate(userId)` | 1 |
| 空值标记读不出来 | 写了一半，读侧没识别 | 命中后判 null 抛异常 | 4 |
| `findByIds` null 元素 / NPE | 同上根因 | 过滤空值标记 + 滤 null | 2 |

**共同根因其实是一个：`"null"` 这个哨兵值只在写入侧存在，读取侧从来没有对应的识别逻辑。**
把它补上，隐患二和隐患三一起解决。
