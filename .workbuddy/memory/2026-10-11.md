## 精读第 2 个文件：UserServiceImpl.findById（三级缓存）

- 精读 `shiguang-user-biz/.../service/impl/UserServiceImpl.java`（688 行）中的 `findById`（378-439 行），连带 `RedisKeyConstants`、`MQConstants`、`DelayDeleteUserRedisCacheConsumer`、`JsonUtils`。
- 交付要点：
  - 三级缓存：`LOCAL_CACHE`(Caffeine, TTL 1h) → Redis(`user:info:{userId}`) → MySQL；回填一律走 `threadPoolTaskExecutor` 异步。
  - 防穿透：DB 查不到 → 异步写字符串 `"null"`，TTL `60 + randomInt(60)` 秒。
  - 防雪崩：正常数据 TTL `1天 + randomInt(1天)` 打散过期时刻。
  - 写路径（`updateUserInfo` 203-213 行）：删 Redis → 写 MySQL → 发 `DelayDeleteUserRedisCacheTopic` 延迟消息（级别 1，约 1s）再删一次 = 延迟双删。
  - 这是项目中第一次出现 MQ：延迟能力靠 RocketMQ 延迟消息而非 `Thread.sleep`；消费者 `DelayDeleteUserRedisCacheConsumer` 实现 `RocketMQListener<String>`。
- **发现两处可疑点（仅记录，未改动代码，待主人核对）**：
  1. `LOCAL_CACHE` / `PROFILE_LOCAL_CACHE` 全项目只有 `put`、没有失效删除（已用 Grep 确认）；多实例部署下更新用户资料不会清掉其他实例的本地缓存，只能靠 TTL 自然过期。对比 note 服务有 `DeleteNoteLocalCacheTopic` 广播，user 服务没有。
  2. 空值缓存写入字符串 `"null"`，读时 `StringUtils.isNotBlank("null")` 为 true → `JsonUtils.parseObject` 返回 null（该方法仅对 blank 返回 null）→ 异步 `LOCAL_CACHE.put(userId, null)` 会因 Caffeine 不接受 null 抛 NPE（被线程池吞掉）→ 最终返回 `Response.success(null)` 而非抛 `USER_NOT_FOUND`。与接手文档 §23.4 的提醒吻合。
- `PROFILE_LOCAL_CACHE` 及其写入方法 `syncUserProfile2LocalCache` / `syncUserProfile2Redis` 的调用点全被注释掉，属死代码。
