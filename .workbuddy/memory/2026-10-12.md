## 「精读项目源码」教学系列（承接 10-11 的三级缓存讲解）

- 主人提问：`UserServiceImpl.findById` 第 431 行缓存回填为何用 `threadPoolTaskExecutor.submit` 而不用 MQ。
- 已核实的项目事实：
  - 线程池定义在 `shiguang-user-biz/config/ThreadPoolConfig.java`：bean 名 `taskExecutor`，core 10 / max 50 / queue 200 / keepAlive 30s / 前缀 `UserExecutor-` / 拒绝策略 `CallerRunsPolicy` / `waitForTasksToCompleteOnShutdown=true`。
  - 该池在 user 模块被多处复用（`UserServiceImpl` 400/413/431/515/667/679，`UserRelation` 371/450）。
  - 项目里确实存在「用 MQ 刷本地缓存」的先例，且都是**广播模式**：
    - `shiguang-note` → `TOPIC_DELETE_NOTE_LOCAL_CACHE = "DeleteNoteLocalCacheTopic"`，消费者 `DeleteNoteLocalCacheConsumer`（`messageModel = MessageModel.BROADCASTING`）。
    - `shiguang-comment` → `TOPIC_DELETE_COMMENT_LOCAL_CACHE = "DeleteCommentDetailLocalCacheTopic"`，消费者 `DeleteCommentLocalCacheConsumer`（同为 BROADCASTING）。
  - 注意二者做的是「**失效（删）**」且必须让所有实例收到；而 user 这里做的是「**回填（写）**」，是进程私事。user 模块**没有**对应的本地缓存失效 Topic —— 呼应 10-11 记录的「user 本地缓存只写不删，最多脏 1 小时」。

## 教学结论（可复用的话术）
- 选 MQ 的三条判据：①需要延迟执行 ②需要跨实例投递（广播）③丢了会留下长期脏数据（必须持久化）。
- 缓存回填三条全不满足：Redis 缓存可重建、本地缓存是进程私有、且 MQ 会把「旧值乱序覆盖新值」的窗口从微秒级放大到秒级。
- 结论：这是**语义错配**问题，不是性能问题。

## 用户缓存隐患修复方案（只写文档，未改源码）

- 产出：`.workbuddy/docs/用户缓存两处隐患_手把手修改方案.md`
- 新增核实的关键事实（后续复用）：
  - `config/RedisTemplateConfig.java` 第 30 行：value 用 `Jackson2JsonRedisSerializer(Object.class)`。故 `set(key,"null")` 落库是 JSON 字符串字面量 `"null"`，读回是 4 字符 String。
  - `JsonUtils.parseObject("null", Clazz)` 返回 Java null（非空白串 → 走 readValue → JSON null）。
  - `Response.success(null)` → `success=true, data=null`（`Response.java` 第 33-37 行）。
  - `threadPoolTaskExecutor.submit()` 返回 FutureTask，异常被**静默吞掉**（连日志都没有）；`execute()` 才会走 uncaught handler。
  - `PROFILE_LOCAL_CACHE` 及其同步方法目前是**死代码**（调用点全被注释）。
- **新发现的第三个 bug（重要）**：`UserServiceImpl.findByIds` 第 458-491 行 ——
  `filter(Objects::nonNull)` 过滤不掉字符串 `"null"`，`parseObject` 转成 null 后：
  ① 若长度恰好相等（475 行）会 `return success([dto1, dto2, null])`，前端遍历 NPE；
  ② 若长度不等会走到 485 行 `Collectors.toMap(FindUserByIdRspDTO::getId, ...)`，对 null 取 getId → **NPE，接口 500**。
- 修复方案分三档：
  - 隐患一（本地缓存只写不删）：A 加 `LOCAL_CACHE.invalidate(userId)`（1 行）；B 照抄 note 的广播模式 Topic（5 文件）；C 缩 TTL（不推荐）。
  - 隐患二（空值标记读不出来）：命中缓存后判 null → 抛 `USER_NOT_FOUND`（4 行）+ `NULL_CACHE_VALUE` 常量。
  - 隐患三（findByIds）：过滤空值标记 + 结果集再滤 null（2 行）。
- 三者共同根因：**`"null"` 哨兵只在写入侧存在，读取侧从未识别**。
- 进阶提醒（方案 A/B 都挡不住）：本地缓存**异步回填 + 同步失效**存在覆盖竞态 —— 请求 A 查旧值提交异步任务，更新流程删缓存后，该任务才把旧值写回。彻底解法是把回填改同步或改用 Caffeine 原子加载，不建议现在动。

## 精读系列第 3 篇：NoteController.java（+ note 的两份常量地图）

已核实的项目事实（重要，后续复用）：

- **`shiguang-note-api` 模块存在但是空壳**：全目录只有一个 `pom.xml`，没有任何 `.java`。
  → 推论：**note 不对外提供任何 Feign 接口**。所以 `NoteController` 的 12 个接口**全部**带
  `@ApiOperationLog`、没有「对其他服务提供的接口」分界线（对比 user 有 user-api、有分界线）。
- `NoteController` 12 个接口三组：写 5（publish/update/delete/visible.onlyme/top，返回 `Response<?>`）、
  成对 4（like+unlike、collect+uncollect）、读 3（detail/isLikedAndCollectedData/published.list，
  返回 `Response<具体VO>`）。规律：**返回体带泛型 = 读，不带 = 写**。
- 成对接口 ↔ MQ 设计：`TOPIC_LIKE_OR_UNLIKE = "LikeUnlikeTopic"`、
  `TOPIC_COLLECT_OR_UN_COLLECT = "CollectUnCollectTopic"` 各自**共用一个 Topic**，靠
  `TAG_LIKE/TAG_UNLIKE/TAG_COLLECT/TAG_UN_COLLECT` 区分；配套枚举 `LikeUnlikeNoteTypeEnum`、
  `CollectUnCollectNoteTypeEnum`。
- note 的 `MQConstants`：9 个 Topic + 7 个 Tag。四类用途：缓存失效（3）、事务消息（1）、
  业务广播（3：LikeUnlike/CollectUnCollect/NoteOperate）、计数（2：CountNoteLike/CountNoteCollect）。
  note 自己只消费其中 5 个（consumer 包），计数类 Topic 的消费者在 count 模块。
- note 的 `RedisKeyConstants`：8 个前缀。`note:detail:`、`note:published:list:`、
  `bloom:note:likes:`、`rbitmap:note:likes:`、`bloom:note:collects:`、`rbitmap:note:collects:`、
  `user:note:likes:`(ZSet)、`user:note:collects:`(ZSet)。**前缀里就写明了数据结构**。
  bloom + rbitmap 并存 = 双层判重（bloom 快速否定，rbitmap 精确判定）—— 待主人自己去
  `likeNote` 验证。
- `PublishNoteReqVO` 里是 `List<String> imgUris` / `String videoUri`（**URI 不是文件**），
  所以 publish 能用 `@RequestBody`；对比 user 的 `updateUserInfo` 因有 `MultipartFile` 必须走 multipart。
  架构含义：**文件先传 OSS 拿 URL，再提交业务请求**，上传与写入解耦。

## 精读系列第 4 篇：NoteServiceImpl.publishNote（唯一使用事务消息的地方）

文件：`shiguang-note/shiguang-note-biz/.../service/impl/NoteServiceImpl.java` 第 112–219 行；
配套 `listener/PublishNote2DBLocalTransactionListener.java`（155 行）、`kv/.../consumer/SaveNoteContentConsumer.java`。

已核实的关键事实（后续复用）：

- **`publishNote` 上没有 `@Transactional`**（对比 `updateNote` 第 424 行有 `@Transactional(rollbackFor=Exception.class)`）。
  原因：它解决的是「本服务写 MySQL + KV 服务写 Cassandra」的跨服务原子性，本地事务管不了。
- 方法体三段：112–146 校验（`NoteTypeEnum` switch + `Preconditions.checkArgument`）；
  148–198 组装 `NoteDO`（分布式 ID `DistributedIdGeneratorRpcService.getNoteId()`、`contentUuid=UUID`、
  话题名 `TopicDOMapper.selectNameByPrimaryKey`、`creatorId = LoginUserContextHolder.getUserId()`）；
  200–219 分流。
- **分流**：`content` 为空白 → `processPublishContentEmptyNote`（227–266，同步路径，不走事务消息）；
  非空 → `sendMessageInTransaction(TOPIC_PUBLISH_NOTE_TRANSACTION, message, null)`（第 214 行）。
- **事务消息闭环**（这是全项目最关键的一条链路）：
  1. note 发 half 消息到 `PublishNoteTransactionTopic`
  2. Broker 回调 `executeLocalTransaction`：删 `note:published:list:` 缓存 → `noteDOMapper.insert(noteDO)`
     → 发延迟双删 MQ → `asyncSend(TOPIC_NOTE_OPERATE + ":" + TAG_NOTE_PUBLISH)` → 返回 `COMMIT`
  3. COMMIT 后 half 转正，**KV 模块的 `SaveNoteContentConsumer` 消费**（consumerGroup =
     `"shiguang_group_PublishNoteTransactionTopic"`），把 `contentUuid` + `content` 写进 Cassandra
  4. 兜底：`checkLocalTransaction` 用 `noteDOMapper.selectCountByNoteId(noteId)` 判定
     `count == 1 ? COMMIT : ROLLBACK`
- **第 162–167 行 `keyValueRpcService.saveNoteContent(...)` 被整段注释掉，这不是 bug**：
  正文改由「事务消息 + KV 消费者」这条异步路保存，注释是同步 RPC 旧方案的残留。
  但注意 **`updateNote` 第 530 行仍在用 `saveNoteContent` 同步 RPC** —— 发布/更新两条路不对称。
- **两条路径的一致性级别不同**：正文为空那条没有事务消息，`insert` 与 `asyncSend` 事件之间无原子性；
  失败只打日志，会导致 count 的发布数少 1（靠 data-align 日增量对账兜底）。这是取舍，不是疏忽。
- `TOPIC_NOTE_OPERATE` 的下游有两个、各拿全量：`count.CountNotePublishConsumer`（计数 ±1）、
  `data-align.TodayNotePublishIncrementData2DBConsumer`（日增量落分片临时表 + 布隆判重）。
- 正文存储实况：`NoteDO` **没有 content 字段**，只有 `contentUuid`；KV 侧
  `NoteContentServiceImpl` 用 `NoteContentRepository`（Spring Data Cassandra）以 UUID 为主键存取。

### 全项目级发现 5：所有模块的 `rocketmq.producer.group` 都叫 `shiguang_group`
（note / count / comment / user / user-relation 的 `application-dev.yml` 第 62–64 行全是同名。）
RocketMQ 约定 producer group 应全局唯一；事务消息回查是按 producer group 找生产者实例的，
同名可能导致回查打到别的服务实例上 → 事务被误判 → 正文丢失。目前只有 note 用事务消息，
本地演示不会暴露。建议改为独立名（如 `shiguang_note_transaction_group`），**属配置改动，未动**。

### ⚠️ 关键风险：同名常量不同值

### 方案要点
- 落点：`shiguang-common` 的 `com.quanshiguang.framework.common.constant` 包（已有 constant 包，且
  **7 个相关模块的 pom 都已直接依赖 shiguang-common**，故 pom 零改动）。
- 公共类命名 `SharedMQConstants`（不能叫 MQConstants，会与各模块本地类 import 冲突）。
- **核心手法：各模块 `public interface MQConstants extends SharedMQConstants`** ——
  利用接口字段可被子接口继承的特性，`MQConstants.TOPIC_XXX` 的**所有调用点零改动**。
- data-align 与 kv 的常量全被上移 → 保留空接口以兼容既有引用。
- 净效果：删约 220 行重复声明，调用点零改动，Topic 字符串值全部不变。
