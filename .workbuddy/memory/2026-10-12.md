## 「精读项目源码」教学系列（承接 10-11 的三级缓存讲解）

- 主人提问：`UserServiceImpl.findById` 第 431 行缓存回填为何用 `threadPoolTaskExecutor.submit` 而不用 MQ。
- 已核实的项目事实：
  - 线程池定义在 `shiguang-user-biz/config/ThreadPoolConfig.java`：bean 名 `taskExecutor`，core 10 / max 50 / queue 200 / keepAlive 30s / 前缀 `UserExecutor-` / 拒绝策略 `CallerRunsPolicy` / `waitForTasksToCompleteOnShutdown=true`。
  - 该池在 user 模块被多处复用（`UserServiceImpl` 400/413/431/515/667/679，`UserRelation` 371/450）。
  - 项目里确实存在「用 MQ 刷本地缓存」的先例，且都是**广播模式**：
    - `shiguang-note` → `TOPIC_DELETE_NOTE_LOCAL_CACHE = "DeleteNoteLocalCacheTopic"`，消费者 `DeleteNoteLocalCacheConsumer`（`messageModel = MessageModel.BROADCASTING`）。
    - `shiguang-comment` → `TOPIC_DELETE_COMMENT_LOCAL_CACHE = "DeleteCommentDetailLocalCacheTopic"`，消费者 `DeleteCommentLocalCacheConsumer`（同为 BROADCASTING）。
  - 注意二者做的是「**失效（删）**」且必须让所有实例收到；而 user 这里做的是「**回填（写）**」，是进程私事。user 模块**没有**对应的本地缓存失效 Topic —— 呼应 10-11 记录的「user 本地缓存只写不删，最多脏 1 小时」。

## 教学结论（可复用的话术）
- 选 MQ 的三条判据：①需要延迟执行 ②需要跨实例投递（广播）③丢了会留下长期脏数据（必须持久化）。
- 缓存回填三条全不满足：Redis 缓存可重建、本地缓存是进程私有、且 MQ 会把「旧值乱序覆盖新值」的窗口从微秒级放大到秒级。
- 结论：这是**语义错配**问题，不是性能问题。

## 用户缓存隐患修复方案（只写文档，未改源码）

- 产出：`.workbuddy/docs/用户缓存两处隐患_手把手修改方案.md`
- 新增核实的关键事实（后续复用）：
  - `config/RedisTemplateConfig.java` 第 30 行：value 用 `Jackson2JsonRedisSerializer(Object.class)`。故 `set(key,"null")` 落库是 JSON 字符串字面量 `"null"`，读回是 4 字符 String。
  - `JsonUtils.parseObject("null", Clazz)` 返回 Java null（非空白串 → 走 readValue → JSON null）。
  - `Response.success(null)` → `success=true, data=null`（`Response.java` 第 33-37 行）。
  - `threadPoolTaskExecutor.submit()` 返回 FutureTask，异常被**静默吞掉**（连日志都没有）；`execute()` 才会走 uncaught handler。
  - `PROFILE_LOCAL_CACHE` 及其同步方法目前是**死代码**（调用点全被注释）。
- **新发现的第三个 bug（重要）**：`UserServiceImpl.findByIds` 第 458-491 行 ——
  `filter(Objects::nonNull)` 过滤不掉字符串 `"null"`，`parseObject` 转成 null 后：
  ① 若长度恰好相等（475 行）会 `return success([dto1, dto2, null])`，前端遍历 NPE；
  ② 若长度不等会走到 485 行 `Collectors.toMap(FindUserByIdRspDTO::getId, ...)`，对 null 取 getId → **NPE，接口 500**。
- 修复方案分三档：
  - 隐患一（本地缓存只写不删）：A 加 `LOCAL_CACHE.invalidate(userId)`（1 行）；B 照抄 note 的广播模式 Topic（5 文件）；C 缩 TTL（不推荐）。
  - 隐患二（空值标记读不出来）：命中缓存后判 null → 抛 `USER_NOT_FOUND`（4 行）+ `NULL_CACHE_VALUE` 常量。
  - 隐患三（findByIds）：过滤空值标记 + 结果集再滤 null（2 行）。
- 三者共同根因：**`"null"` 哨兵只在写入侧存在，读取侧从未识别**。
- 进阶提醒（方案 A/B 都挡不住）：本地缓存**异步回填 + 同步失效**存在覆盖竞态 —— 请求 A 查旧值提交异步任务，更新流程删缓存后，该任务才把旧值写回。彻底解法是把回填改同步或改用 Caffeine 原子加载，不建议现在动。

## 精读系列第 4 篇：NoteServiceImpl.publishNote（唯一使用事务消息的地方）

文件：`shiguang-note/shiguang-note-biz/.../service/impl/NoteServiceImpl.java` 第 112–219 行；

已核实的关键事实（后续复用）：

- **`publishNote` 上没有 `@Transactional`**（对比 `updateNote` 第 424 行有 `@Transactional(rollbackFor=Exception.class)`）。
  原因：它解决的是「本服务写 MySQL + KV 服务写 Cassandra」的跨服务原子性，本地事务管不了。
- 方法体三段：112–146 校验（`NoteTypeEnum` switch + `Preconditions.checkArgument`）；
  148–198 组装 `NoteDO`（分布式 ID `DistributedIdGeneratorRpcService.getNoteId()`、`contentUuid=UUID`、
  话题名 `TopicDOMapper.selectNameByPrimaryKey`、`creatorId = LoginUserContextHolder.getUserId()`）；
  200–219 分流。
- **分流**：`content` 为空白 → `processPublishContentEmptyNote`（227–266，同步路径，不走事务消息）；
  非空 → `sendMessageInTransaction(TOPIC_PUBLISH_NOTE_TRANSACTION, message, null)`（第 214 行）。
- **事务消息闭环**（这是全项目最关键的一条链路）：
  1. note 发 half 消息到 `PublishNoteTransactionTopic`
  2. Broker 回调 `executeLocalTransaction`：删 `note:published:list:` 缓存 → `noteDOMapper.insert(noteDO)`
     → 发延迟双删 MQ → `asyncSend(TOPIC_NOTE_OPERATE + ":" + TAG_NOTE_PUBLISH)` → 返回 `COMMIT`
  3. COMMIT 后 half 转正，**KV 模块的 `SaveNoteContentConsumer` 消费**（consumerGroup =
     `"shiguang_group_PublishNoteTransactionTopic"`），把 `contentUuid` + `content` 写进 Cassandra
  4. 兜底：`checkLocalTransaction` 用 `noteDOMapper.selectCountByNoteId(noteId)` 判定
     `count == 1 ? COMMIT : ROLLBACK`
- **第 162–167 行 `keyValueRpcService.saveNoteContent(...)` 被整段注释掉，这不是 bug**：
  正文改由「事务消息 + KV 消费者」这条异步路保存，注释是同步 RPC 旧方案的残留。
  但注意 **`updateNote` 第 530 行仍在用 `saveNoteContent` 同步 RPC** —— 发布/更新两条路不对称。
- **两条路径的一致性级别不同**：正文为空那条没有事务消息，`insert` 与 `asyncSend` 事件之间无原子性；
  失败只打日志，会导致 count 的发布数少 1（靠 data-align 日增量对账兜底）。这是取舍，不是疏忽。
- `TOPIC_NOTE_OPERATE` 的下游有两个、各拿全量：`count.CountNotePublishConsumer`（计数 ±1）、
  `data-align.TodayNotePublishIncrementData2DBConsumer`（日增量落分片临时表 + 布隆判重）。
- 正文存储实况：`NoteDO` **没有 content 字段**，只有 `contentUuid`；KV 侧
  `NoteContentServiceImpl` 用 `NoteContentRepository`（Spring Data Cassandra）以 UUID 为主键存取。

### 全项目级发现 5：所有模块的 `rocketmq.producer.group` 都叫 `shiguang_group`

## 精读系列第 5 篇：NoteServiceImpl.likeNote（全项目性价比最高的一条链路）

文件：`shiguang-note-biz/.../service/impl/NoteServiceImpl.java` 第 745–899 行（150 行）。
配套：3 个 Lua（`rbitmap_note_like_check.lua` / `rbitmap_add_note_like_and_expire.lua` /
`note_like_check_and_update_zset.lua`）、`enums/NoteLikeLuaResultEnum`、
`consumer/LikeUnlikeNoteConsumer`、`count/.../CountNoteLikeConsumer`、
`count/.../CountNoteLike2DBConsumer`、`data-align/.../TodayNoteLikeIncrementData2DBConsumer`、
`recommend/.../UserInterestByLikeConsumer`。

已核实的关键事实（后续复用）：

- 方法五步：①`checkNoteIsExistAndGetCreatorId`（三级缓存回源）②Lua 原子判重 ③更新点赞 ZSet
  ④`asyncSendOrderly` 发 MQ ⑤`Response.success()`。**方法内没有任何一句写 MySQL** —— 落库在消费者。
- **Lua 返回值即业务语义**：`-1`=NOT_EXIST（无 bitmap，冷启动）/ `1`=NOTE_LIKED（已点赞，直接抛
  `BizException(NOTE_ALREADY_LIKED)`）/ `0`=成功**且此刻已 `R.SETBIT` 写入**。
  → 「判重」与「写入」在同一次 Lua 调用内完成，中间无缝隙；这是必须用 Lua 而非两次 redisTemplate 调用的原因。
- `NOTE_LIKED` 分支第 802–817 行有大段**被注释掉的** ZSet/DB 二次校验代码，现已被简化为直接抛异常。
- ZSet（`user:note:likes:`）语义 = **最近点赞的 100 篇**（`note_like_check_and_update_zset.lua` 里
  `size >= 100 → ZPOPMIN` 踢掉分最低的），不是全量。
- **顺序消息是配套设计**：生产侧 `asyncSendOrderly(destination, msg, hashKey=userId)`，
  消费侧 `consumeMode = ConsumeMode.ORDERLY`。**hashKey 选 userId 而非 noteId** 是刻意的 ——
  同一用户的「赞/取消赞」必须落同一队列按序处理，否则「先赞后取消」会被乱序执行。
- 点赞 MQ 的两段式：`TOPIC_LIKE_OR_UNLIKE`（note 生产；note 自己 + recommend 消费）
  → note 消费者写 `t_note_like` 后**转发** `TOPIC_COUNT_NOTE_LIKE`（count + data-align 消费）。
- `LikeUnlikeNoteConsumer` 幂等靠 `t_note_like` 的**联合唯一索引** + `insertOrUpdate`；
  另有 `RateLimiter.create(5000)` 做流量削峰；`ConsumeMode.ORDERLY` 顺序消费。
- `CountNoteLikeConsumer` 用 `BufferTrigger.batchBlocking()`（bufferSize 50000 / batchSize 1000 /
  linger 1s）聚合，按 noteId 分组把 ±1 求和，**且仅当 Redis Hash 已存在才 increment**
  （`hasKey` 判断），然后 `asyncSend(TOPIC_COUNT_NOTE_LIKE_2_DB)`。
- `CountNoteLike2DBConsumer` 用 `TransactionTemplate` 编程式事务，一条事务内
  `noteCountDOMapper.insertOrUpdateLikeTotalByNoteId` + `userCountDOMapper.insertOrUpdateLikeTotalByUserId`。
- `recommend.UserInterestByLikeConsumer` 从 **ES** 查笔记 topic（`GetRequest("note", noteId)` 只取
  source 的 `topic` 字段），再对 `user:interest:topic:{userId}` ZSet 做 `incrementScore(topic, ±1)`，
  并 `expire 7 天`。
- **search 不订阅任何 MQ**：ES 文档里的 `like_total` 只在建索引/重建时写入
  （`search/.../NoteServiceImpl` 第 299 行从 `sourceAsMap` 读取），故**搜索页点赞数长期滞后**。
- count 的 Redis Hash（`count:note:{noteId}`）**懒初始化 + 随机 TTL**：
  `NoteCountServiceImpl.syncNoteHash2Redis` 第 181 行 `expireTime = 60*30 + RandomUtil.randomInt(60*30)`
  （即 30–60 分钟）；读路径用 **Pipeline `multiGet`** 批量取 3 个 field，**任一 field 为 null 就回源 DB**，
  回源后用 `executePipelined` + `putAll` 只补 null 的 field（不覆盖已有值）。

## 两道练习的答案（已核实）

### 练习 1：bitmap / ZSet 的 TTL 为什么是「1 天 + 随机 0~1 天」
- **主因与 user 模块那次相同：随机 TTL 打散过期时刻（防雪崩）**，但这里动机强得多，三点加成：
  1. **回源成本高一个量级**：user 那边回源是 `selectByPrimaryKey`（走主键，一行）；这里
     `batchAddNoteLike2RBitmapAndExpire` 回源是 `noteLikeDOMapper.selectByUserId(userId)` ——
     **该用户全部点赞记录**。同时过期 = 同时发起大量全量查询。
  2. **写时创建 + 每次写重置 TTL（滑动过期）**：两个 Lua 都是先 `SETBIT`/`ZADD` 再 `EXPIRE`，
     所以活跃用户永不失效，只有静默 1~2 天的用户才过期 —— 而「同一批用户同时静默」正是
     流量高峰过后最容易出现的情况，批量过期 → 批量回源。
  3. 同时防**冷启动风暴**：NOT_EXIST 分支的 `selectCountByUserIdAndNoteId`（便宜）
     与异步全量重建（昂贵）都会被触发。
- 与「防穿透」无关：这里没有写空值哨兵。

### 练习 2：count 为什么不直接写 DB，非要「先改 Redis + 再发 `_2_DB`」
- **两层原因，缺一不可**：
  1. **写成本差 2~3 个数量级**：Redis `HINCRBY` 是纯内存单命令；MySQL `UPDATE` 要走 WAL、加行锁、
     可能触发页分裂。点赞是典型「高频强写」场景（热点笔记可达万级 QPS），DB 扛不住 —— 必须用 Redis 挡在前面。
     再叠加 `BufferTrigger`（batchSize 1000 / linger 1s）把 1000 次更新合并成 1 条消息、1 次批量 UPDATE，
     实际 DB 写入量再降约 1000 倍。
  2. **计数的 Hash 是「基线 + 增量」模型，基线必须来自 DB**：所以
     `CountNoteLikeConsumer` 里那句 `if (isCountNoteExisted) { increment }` 不是随手写的 ——
     Redis Hash 不存在时说明基线还没建立，此时若直接 `INCRBY`，会造出一个 `likeTotal = 1`
     的 Hash（真实值可能是 501），**凭空生成一个错误的基线**。正确做法是跳过 Redis、
     交给下一次读取时由 `NoteCountServiceImpl` 从 DB 初始化完整基线（DB 侧此刻已由 `_2_DB` 轨更新）。
- 一句话总结：**Redis 是"读"的服务对象，MySQL 是"基线"的权威来源；用异步消息把两者解耦**，
  这也是 Cache-Aside + 异步刷库的典型形态。

## 面试话术：随机 TTL 防雪崩（练习一的口述版）

主人要求把「练习一」转成面试可直接说的话术，已产出三档脚本（30 秒 / 1~2 分钟 / 追问应对）。
要点固化（后续复用，不必重写）：

- **定位**：这是**防雪崩**（大量 key 同时失效），不是防击穿（单个热点 key 失效 → 逻辑过期/互斥锁），
  也不是防穿透（查不存在的 key → 空值哨兵）。bitmap 是 **per-user** key，天然属于"大批量同时创建"，
  所以是雪崩场景。
- **手法一句话**：`expireSeconds = 86400 + random(0, 86400)`，即 1 天起步、再随机铺开一整天。
- **可复用的两句话**：
  1. 「TTL 的真实职责是**回收冷用户内存**，不是保证新鲜度 —— 因为每次写操作都会 `EXPIRE` 重置，
     活跃用户永远不过期，数据新鲜度是靠写操作维护的。」
  2. 「随机区间的宽度要和『批量创建的规模』匹配：这里给到整整一天，是因为回源是全量查询，
     宁可摊得极开也不能形成尖峰。」
- **本项目的加分点（对比 user 模块）**：`UserServiceImpl.findById` 回源是 `selectByPrimaryKey`（一行），
  这里回源是 `noteLikeDOMapper.selectByUserId`（该用户全部点赞记录）—— **同一个手法，回源成本差一个量级**，
  所以在这里收益更大。能主动做这个横向对比是加分项。
- **三个别说的坑**：①别把它归为「防穿透」；②别只答「防止缓存同时失效」就停住，要接上"回源代价"；
  ③别把随机 TTL 说成"保证一致性"的手段，它和一致性无关。
- **追问预案**：为什么不用固定 TTL + 定时预热 / 随机了还同时过期怎么办 / TTL 为什么是 1~2 天而不是 1 小时
  （答案：冷用户内存回收周期，太长则内存浪费，太短则回源频繁）。

### 里程碑 2 分析（只读，未改码）

**骨架实际状态已比上面记录的更靠前**（主人后续自行补了代码）。截至 10-12 晚核对：

已实现（可直接跑）：
- `engine/SensitiveWordFilter`：Trie + 词库加载（`sensitive-words.txt` 8 个词）全部实现。
- `engine/ModerationEngine.judge`：敏感词 + TOO_LONG/EXTERNAL_LINK/REPEAT_CHAR 四规则，已实现。
- `mq/ContentReviewProducer.send`：已实现（key=contentId，`whenComplete` 回调）。
- `mq/ModerationEngineConsumer.onMessage`：已实现 **但串上了未实现的 save**。
- `mq/ModerationStatConsumer.onMessages`：已实现（Redis HINCRBY 按天累加，OK）。
- `config/ModerationIndexInitializer`：**真连 ES**（`GetIndexRequest` + `indices().exists`），
  ⚠️ 与上面「刻意不真连 ES」的记录**相反** —— 实际会在启动期连接 ES。

仍占位（抛 `UnsupportedOperationException`）：
- `repository/ModerationRecordRepository.save` / `saveBatch`
- `controller/ModerationTestController.mockEvent`
- `service/impl/ModerationServiceImpl` 的 search / trend / hotHitWords / overview 四个方法

**核心结论：里程碑 2 与里程碑 3 在现有骨架上已被"焊死"。**
`ModerationEngineConsumer` 依次调 `judge`（已实现）→ `save`（占位抛异常）→ `ack`。
所以消息一进来必然在 save 处炸：异常 → `DefaultErrorHandler`（FixedBackOff 1000ms×3）→ 重试 3 次
→ `DeadLetterPublishingRecoverer` 投到 `shiguang.content.review.DLT`（恢复成功后位点才会被跳过），
**`ack.acknowledge()` 永远执行不到**。因此"只打通 Kafka、先不审核"这个中间态在当前骨架里不成立。
两条路：① 合并做里程碑 3（补 `save`，约 20 行）——推荐；② 临时注释掉 consumer 里的 judge/save 两行。
（side note：stat 组已完整实现且是**独立消费组**，所以即使 engine 组一直失败，stat 组照样正常消费
—— 这本身就是"多消费组互不影响"的现成演示。）

**另外三个里程碑 2 的前置/坑（本次核实）**：
1. **启动应用必须 ES 在线**（`ModerationIndexInitializer` 是 `ApplicationRunner`，启动期真连
   `127.0.0.1:9200`；ES 不在 → 连接拒绝 → 启动失败）。哪怕只想练 Kafka 也躲不开，是隐性环境耦合。
2. **DLT topic 分区数必须与主 topic 一致**：`DeadLetterPublishingRecoverer` 用
   `new TopicPartition(topic + ".DLT", record.partition())` —— **沿用原消息的分区号**。
   文档 2.3 让手动建 1 分区的 DLT，若原消息在 partition 1/2 会投递失败。规避：建 DLT 时也用
   `--partitions 3`，或干脆不手动建、交给自动创建（docker-compose 里 `KAFKA_NUM_PARTITIONS: 3`）。
3. **待实测**：`KafkaConfig.kafkaErrorHandler` 只显式设给了批量容器；engine 组用 Boot 自动配置的默认容器，
   是否会自动接上这个 `DefaultErrorHandler` bean 需实测（发一条必失败的消息看有无"重试 3 次 + DLT"）。

其他已核实的配置：`application-dev.yml` 已切到 `spring.kafka.listener.ack-mode: manual_immediate`；
`missing-topics-fatal: false`；Redis 用 database 1；`ThreadPoolConfig` bean 名 `taskExecutor`、
前缀 `ModerationExecutor-`（注意与 note 的同名 bean `taskExecutor` 同名，但不同模块互不影响）。
